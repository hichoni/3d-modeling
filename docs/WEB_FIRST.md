# 제품 목표: 크롬북·노트북의 웹에서 슬라이싱과 로컬 출력

## 사용자 의도 · 2026-10-20 재확인

제품의 중심은 **웹에서 모델링 → 실제 슬라이싱 → 출력 미리보기 → 현장에서 매칭한 A1 mini 출력 시작**까지 이어지는 체험입니다. 참가자는 크롬북이든 노트북이든 브라우저 하나를 사용합니다. Windows 운영 앱 자체를 별도 주력 제품으로 출시하는 것이 목표가 아닙니다.

부스는 크롬북 6대와 A1 mini 6대의 현장 1:1 매칭을 기본으로 합니다. 사용자는 공용 노트북 한 대를 추가할 수 있다고 밝혔습니다. 이 기기를 사용하더라도 참가자에게 Bambu Studio나 별도 설정 앱을 조작하게 하지 않습니다.

## 현재 구현과 다음 목표의 차이

| 기능 | 현재 확인된 구현 | 다음 검증 목표 |
| --- | --- | --- |
| 모델링·층 체험 | 브라우저 | 유지 |
| 실제 슬라이싱 계산 | 공용 Windows PC의 Bambu Studio CLI | 브라우저의 FDM 엔진 |
| 실제 출력 경로 표시 | Bambu Studio 결과를 웹에 표시 | 웹 엔진이 생성한 실제 경로 표시 |
| 현장 1:1 매칭·운영자 확인 | 웹 + 인증된 로컬 서버 | 기존 권한·프린터 분리를 유지 |
| 프린터 파일 전송·시작·상태 | 로컬 서버의 FTPS·TLS MQTT | 연결 중계기로 역할 분리 |
| 참가자 설치 | 없음 | 없음 |
| Bambu Studio 필요 여부 | 공용 PC에 필요 | 새 경로 검증 후 제거 가능한 의존성. 아직 제거하지 않음 |

현재 GitHub Pages가 브라우저 안에서 실제 슬라이싱까지 수행한다고 안내하지 않습니다. 기존 교육용 층 화면을 실제 슬라이싱으로 재표시하거나, 새 엔진의 A1 mini 출력을 검증한 것처럼 설명하지 않습니다.

```text
목표: 크롬북·노트북의 웹
      모델링 → 실제 슬라이싱 → 경로 확인 → 출력 버튼
                            ↓
                 현장 연결 중계기 한 대
                  프린터 통신·접수·권한
                            ↓
               현장에서 매칭한 A1 mini
```

브라우저는 프린터의 원시 TCP 기반 FTPS·MQTT 연결을 일반 웹 API로 직접 열 수 없습니다. 프린터가 브라우저용 통신 인터페이스를 제공하거나 지원되는 별도 연결 기능이 확인되지 않는 한 로컬 중계는 남습니다. 따라서 **크롬북 6대 + 프린터 6대만으로 추가 연결 장치가 전혀 없는 순수 웹 직결은 확인하지 못했습니다.**

## 조사로 확인한 것

- [Kiri:Moto 공개 엔진 API](https://grid.space/kiri/engine.html)는 STL 입력, 레이어 슬라이싱, 경로 준비, G-code 생성을 제공합니다. 브라우저 내 실제 계산을 통합할 근거가 있습니다.
- [공개 소스](https://github.com/GridSpace/grid-apps)에는 JavaScript 슬라이싱 API와 Bambu 연결 모듈이 있습니다. 확인한 트리에는 `src/kiri/dev/fdm/Bambu.A1.json`이 있으나 A1 mini 전용 프로필은 찾지 못했습니다. A1 프로필을 mini에 그대로 사용하지 않습니다.
- [제작자의 Bambu 연결 설명](https://forum.grid.space/t/setting-my-bambu-a1-on-kiri-moto/2715)은 브라우저의 슬라이싱과 로컬 서버의 프린터 연결을 구분합니다.

이 근거는 아키텍처의 구현 가능성에 대한 근거입니다. 우리 앱의 브라우저 엔진 통합, 실제 ChromeOS 성능, A1 mini용 시작·종료 절차, 3MF 호환성과 실물 출력 완료의 증거는 아닙니다.

## 먼저 검증할 작업

1. 실제 브라우저 엔진으로 14mm 모델의 외곽·벽·채움·층별 압출 경로와 G-code를 생성합니다. 교육용 표시와 분리합니다.
2. 0.4mm·외부 PLA·텍스처 PEI·A1 mini의 180mm 베드에 맞는 프로필과 시작·종료 절차를 검증합니다. A1용 좌표·보정 동작을 복사하지 않습니다.
3. 파일 형식과 전송 경로를 검증합니다. 기존 서버는 Bambu Studio로 만든 파일만 받으므로, 브라우저가 임의 G-code를 올리면 무조건 출력하는 API로 바꾸지 않습니다.
4. 프린터 주소가 없는 격리 시험 → 파일·경로 검토 → 사용자가 준비한 실제 한 세트 시험 → 6대 현장 시험 순서로 확인합니다. 물리 출력은 기존 확인 절차를 유지합니다.
5. 검증 후 중계기 설치·서명 방식을 정합니다. Store 계정 등록을 웹 슬라이싱 검증보다 먼저 완료해야 하는 필수 단계로 안내하지 않습니다.

이미 만든 Windows 앱과 서명·MSIX 도구는 중계기 배포의 보조 자산으로 남깁니다. 개인 명의 Store 경로를 선택한 기록은 유지하지만 실제 계정 등록·신분 확인·Store 제출은 아직 하지 않았습니다.
